# Report stage investigation

Measured 2026-09-30 on local combined drafts #93–#97. Exact revision and tree are preserved in the [six raw measurements](benchmarks/0.10-report-stage-measurements.json). This is a development investigation, not release approval.

## Method

The same 100,000-row, 96-cell, 12-temperature, single-group synthetic fixtures as the resource characterization were generated outside measurement. Each steady/event-pressure case ran three times in a fresh process. `perf_counter` wrappers timed existing functions without changing their returned values. Workload module imports were completed first; no RSS sampler or deterministic CPU profiler ran during these measurements. These are elapsed times, not CPU self-times. No local test/build workloads ran concurrently.

The pressure fixture produced exactly 100,000 events, all 100,000 rows were analyzed, and none were excluded. The benchmark captures CLI JSON stdout and decodes it back into a result; that final decode is harness overhead, not part of an ordinary CLI invocation. It is timed separately below. Total includes capture, source snapshot/provenance, analysis, JSON, HTML and decode; it excludes cold workload imports and terminal rendering speed.

## Median elapsed seconds

| Stage | Steady | Event pressure |
| --- | ---: | ---: |
| Analysis and report-series collection | 0.828 | 2.174 |
| Canonical JSON rendering | 0.000 | 0.899 |
| HTML rendering | 0.007 | 1.050 |
| HTML rendering and writing | 0.007 | 1.097 |
| Violation table (inside HTML) | 0.000 | 0.309 |
| Plots (inside HTML) | 0.006 | 0.677 |
| Benchmark JSON decode | 0.000 | 0.255 |
| Captured report workload total | 0.967 | 4.601 |

Nested measurements overlap: table and plots are within HTML rendering, and rendering is within writing. Do not sum all rows. Medians of separate stages need not add up to the median total. The import/sampler differences mean these totals cannot be read as improvements over the earlier end-to-end RSS benchmark.

The cost is distributed between event construction, JSON encoding and complete HTML evidence. This measurement does not isolate a dominant allocation or justify a new processing framework, event truncation, or a changed result schema. The event-heavy HTML remains about 55.5 MiB. A zero-event report is much cheaper, but it does not represent the high-event case.

An initial `cProfile` run around the RSS-sampled benchmark produced inconsistent cumulative attribution, including cumulative thread times greater than elapsed time. Those statistics were discarded. The wall-time wrappers above supply the reported evidence; no optimization claim rests on that CPU profile.

## Reproduction

Install the intended checkout with `pip install -e '.[dev,mf4]'`. Generate fixtures with the existing benchmark's `_write_synthetic_mf4` helper using `rows=100000`, `cells=96`, `temperatures=12`, `layout="single-group"`, and either `scenario="steady"` or `"event-pressure"` (see its integration tests). Then run each case in three fresh processes:

```sh
python benchmarks/profile_report_stages.py /path/to/event-pressure.mf4 /path/to/report.html > stage-measurement.json
```

The diagnostic supports the main CLI and the AnalysisService draft; its environment field records the source revision/tree. Run it as a script, not inside a long-lived application: its instrumentation temporarily wraps module functions. The HTML destination is intentionally replaced on success.

## Confirmed correctness finding

Inspection of the large-output path found that both HTML and JSON writers registered their temporary filename after the first write. A partial write exception therefore left a temporary file behind, even though the intended destination was not replaced. Four fault-injection cases reproduced this with fresh and pre-existing destinations. Draft PR #98 moves registration before writing; complete-output bytes and atomic replacement behavior are preserved. This is output failure cleanup, not a performance optimization.
