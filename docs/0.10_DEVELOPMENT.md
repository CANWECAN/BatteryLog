# 0.10 development checkpoint

0.10 is not released. `0.10.0.dev0` identifies development builds; it is not a
release candidate or a claim that the 0.10 scope is complete. The release-version
check rejects development versions even if a matching tag is supplied.

## Baseline and review branches

The published baseline remains `v0.9.2`. The merged architecture and evidence
hardening checkpoint is `fe02dd7af44b5e0f16badaee6887d3723b4914c1`.

- [PR #93](https://github.com/CANWECAN/BatteryLog/pull/93) contains independent
  semantic anchors and source-distribution test-corpus checks.
- [PR #94](https://github.com/CANWECAN/BatteryLog/pull/94) separates development
  metadata from the published version and records post-release changes.

- [PR #95](https://github.com/CANWECAN/BatteryLog/pull/95) adds the measurement
  contract and common analysis service, preserving the existing API.
- [PR #96](https://github.com/CANWECAN/BatteryLog/pull/96) adds opt-in semantic
  checks for consumers of the frozen result-v8 contract.
- [PR #97](https://github.com/CANWECAN/BatteryLog/pull/97) corrects Linux RSS
  measurement and characterizes aligned two-group MF4 and event pressure.

All five drafts require review before integration. A green test matrix on these
branches is evidence for those changes, not completion of the release gates.

## Open release gates

- [ ] Define the measurement contract: canonical signal identity, supported
  numeric representation, physical units, timestamp/alignment assumptions,
  optional-signal availability, and complete-series topology responsibility.
- [ ] Define and implement the common analysis-service entry point for CLI and
  future desktop callers, with one effective configuration and one result
  authority. Preserve the supported Python API behavior or document migration.
- [ ] Resolve the result-consumer semantic-validation decision tracked in
  [#60](https://github.com/CANWECAN/BatteryLog/pull/60),
  [#63](https://github.com/CANWECAN/BatteryLog/pull/63), and
  [#66](https://github.com/CANWECAN/BatteryLog/pull/66). Keep the published v8
  schema frozen; any successor contract must have a distinct version.
- [ ] Validate the agreed workflows with independent expected evidence,
  including real MF4 ingestion and both current polarities. The CORA campaign
  alone does not establish correctness of every engineering rule.
- [ ] Characterize large-log limits for high event counts and representative
  MF4 layouts. Do not infer an end-to-end memory bound from loader chunk size.
- [ ] Complete a fresh integration review and full Linux/Windows/MF4/package
  matrix on the exact candidate commit. Verify both installed artifacts and
  the test corpus shipped in the source distribution.
- [ ] Reconcile documentation, compatibility decisions and release notes with
  the implemented scope before selecting a release version or creating a tag.

## Working checkpoint: 2026-09-30

A local combination of #93–#97 passed 1,014 tests with the actual MF4 backend,
with 98.53% coverage. Format, lint and type checks passed, and its source package
preserved the independent test corpus and all 32 resource measurements. This
local check is not the final exact-candidate Linux/Windows integration matrix.
The release gates above remain open until their decisions and changes have been
reviewed and integrated; implementation in a draft alone does not close them.

The resource characterization found source/layout-dependent memory and large
HTML output under event pressure: 100,000 events produced about 55.5 MiB of HTML.
The next bounded investigation is to profile the existing event-pressure report
path before selecting a small optimization. Preserve complete evidence and the
frozen v8 result contract. Measurements do not justify a new processing framework.
Desktop GUI work remains in the later launcher milestone. No merge, tag or 0.10
release is authorized by this checkpoint.
